## 三、核心要素

### 1. 真问题：真实痛点与用户角色

**真实业务场景**

用在运营商计费投诉的一线运维值班。前辈的做法是准备一份值班文档，里面是常见 SQL。接到工单后，按工单上的号码和月份套进去，把这个号码整月的流量收费记录拉成一张列表，再对照客户给出的数字自己加总。加总对得上，这张单就结束。生产 SQL 仍由运维在堡垒机上执行。

**一线真实痛点**

值班文档里的 SQL 本身能查出清单。慢在两段人手：从文档里挑语句并填号码、对着整月列表一笔笔加。工单如果给的是主号，而费用在共享池副卡上，同一份 SQL 拉出来的整月列表就是 0。人按这个列表加总，结论也会是「这个号码没用过」。金标准里就有这种单：主号只有本地和内地、费用为 0，主张金额在副卡的香港流量上。

AI 适合接在这份值班文档后面：常见 SQL 收成已验证碎片，号码和月份自动填入；整月科目由查询汇总，人不用笔算；工单号码只是找共享池的入口，主张金额没有出现在某一张卡的行上时，不能把 0 元清单当成查完。

**目标用户角色**

核心使用者是按值班文档处理计费投诉的一线运维。要解开的制约是：每张单都要把整月清单手算一遍，而且工单号码给错时，手算会把错误清单算成结论。

### 2. 真工具：AI 做法与搭建过程

路线 B、路线 C 未使用，已删除。

#### 路线 A：智能体（AI Agent）

**智能体角色设定**

它是计费投诉取证与证据核验助手。专业能力是：把自然语言工单收成号码、账期和主张；判断这张单要核话单金额、用量，还是短信、延误、减免等不能靠话单加总回答的问题；只点名已验证 SQL 碎片出包；读贴回结果；在证据没盖住全部主张时拒绝结案，并给出补查动作。它不扮演“可以手写 Oracle、可以直接宣布计费无误”的计费专家。

**知识库来源**

来自一线运维已经验证过的取证材料，存在本地 SQLite，不是把 CRM 文档做向量检索后直接生成答复。出厂库规模：

- 12 条已验证 SQL 碎片，覆盖订购、共享池成员、流量普查、按日用量、漫游、批价、漫游明细、资费扇区、流量费用和明细、语音明细和资费。
- 166 条表用途，说明计费话单、销售品、短信、电渠、实名、缴费等表用来干什么。表用途不参与出包。
- 180 张卡片：表说明、计费事件、销售品口径、列含义，以及三条禁令（不要先探整表列、不要在话单上做会空结果的自关联、不要只查工单号码就下“没有这笔钱”）。
- 7 条运维策略。其中一条把“只查主号就结案”记为失败。
- 3 张脱敏金标准旧单，类型分别是：未出国却出现国际漫游数据费；主号未出行，费用在共享池副卡；语音套餐仍产生本地数据按量费用。

相似旧单最多返回 3 条，只作提示，不能代替本次贴回。

**使用工具名称**

未使用飞书 Aily、Coze 或 Dify。运行时是自建智能体，关键搭建如下：

1. 模型只通过工具进入闭环。本机工作台使用 Hugging Face smolagents 的 ToolCallingAgent，默认模型为 `deepseek-v4-flash`（可用环境变量替换）。另一入口是 stdio MCP，工具集与工作台相同。
2. 工具落到固定状态机：锁定工单、按碎片名拼 SQL、原样保存贴回、核对、写草稿、确定性核验、人工确认、归档或废弃。
3. SQL 由已验证碎片拼接，填入本单号码和账期。未验证碎片不能出包。模型禁止手写 Oracle，也禁止套用一份固定普查 SQL。
4. 人在堡垒机或既有生产 SQL 环境复核后执行只读查询，从结果网格连表头复制贴回。系统只绑定 `127.0.0.1`。
5. 贴回后的四层核验由代码执行，不调用模型当裁判。检查对象和账期、SQL 与列名与主张金额、每个主张是否有对应证据、结论文字是否超出证据。主张、SQL、贴回或草稿一变，证据指纹作废，旧的通过不能沿用。
6. 核验通过后，智能体必须先展示结果并等待人明确确认，才能确认并归档。证据不足时给出下一步补查，不能写成计费无误。废弃单记入历史，不会假装结案。

**核心系统指令 / Prompt 结构**

下面按运行中的约束整理成三段。工作台和 MCP 使用的就是这些限制，不是另写的参赛人设。

```plaintext
角色设定 (Role):
你是计费投诉取证助手，服务一线运维。对用户只说中文。
你负责拆开这张工单要核什么，并只通过工具推进闭环。
你不是生产库操作员，不持有生产账号，不执行 SQL。

任务目标 (Objective):
把投诉收成号码、账期和主张。
话单金额或用量，才点名已验证碎片出包。
短信通知、延误、减免政策，以及不是话单行加总能回答的问题，不要出流量普查。
人贴回结果之前，不要核对，不要结案。
证据盖住全部主张之前，不要写计费无误，不要归档。

工作步骤 (Workflow):
1. 锁定槽位：号码、账期、主张。已锁定的单不要重开。
2. 自己判断要核的主张。出包必须点名碎片名称，禁止套一份固定 SQL，禁止手写 Oracle。未验证碎片不出包。
3. 把拼好的 SQL 交给人。人复核账号、账期、表和字段后，在生产环境执行，原样贴回。无行按空结果处理，不要套“本表未找到”结案。
4. 贴回即权威。有费为 0、主张金额没对上，不要套别的工单口径，不要直接结案。要再查就点名不同碎片，禁止同一份 SQL 再出一次。
5. 系统做四项核验：对象和账期、SQL 与列名与金额、每个主张是否有证据、结论是否超出证据。缺一项就说明缺口和下一步补查。
6. 核验通过后，先展示结果并等待用户明确确认。只有明确确认后才确认，再归档。否则废弃。废弃不是结案。
```

### 3. 真数据：应用效果与量化交付

快，是相对「做对的手工」少掉两段人耗。执行 SQL 的等待两边一样，不计入。不写跨部门次数：这个工位原来就不过部门。不写小时：基线是拉一张整月清单再手算，不是数小时排查。

**处理时间**

| | 改造前 | 使用 BE 后 |
|---|---|---|
| 人要做的 | 从值班文档挑 SQL，填工单号码和月份，执行，对整月列表手算，看完就回 | 贴工单，执行已经拼好的 SQL，贴回后确认 |
| 固定少掉的 | — | 挑 SQL 并填空；整月列表手算。科目汇总由查询分组求和，核验再对主张金额 |
| 两边都有的 | 在堡垒机执行 SQL | 在堡垒机执行 SQL |

主号清单为 0、费用在副卡上的单，手工若要做对，还要再想起共享池、改一次 SQL、再手算一张列表。BE 用池内成员和有费明细出第二包，加总仍不靠人。所以无论工单号码对不对，人做的都比原来少。分钟数没有秒表记录，30 秒句不写未测的分钟。

**人工参与节点**

改造前 5 步，全是同一名运维：选 SQL、填号码和月份、执行、手算、回单。0 次跨部门。

改造后 3 步，仍是同一名运维：贴工单、执行、贴回后确认。0 次跨部门。对不上主张金额时，执行会再来一次，人仍不用手算，也不能把 0 元清单写成没有这笔。

**量化业务收益**

3 张脱敏金标准里，有 1 张按「工单号码的整月清单手算为 0 就回单」会错结：费用在共享池副卡上。BE 的结案条件是主张金额出现在某一张卡的行上，这种错结过不了归档。另外 2 张里，短信上的金额只是其中一笔、不是整月合计；语音套餐的清单能够加平，但加平只说明话单在，不写成计费无误，也不把减免说成错账。

不写赢单率或未测算的百分比。

**已经能核对的系统事实**

| 指标 | 结果 | 口径 |
|---|---|---|
| 模型直连生产库 | 0 次 | 运行时没有生产库账号，也没有执行 SQL 的入口 |
| 模型自动执行生产 SQL | 0 次 | SQL 只组装；执行在堡垒机，由运维完成 |
| 未核验或未经人工确认即归档 | 流程拒绝 | 须先通过代码核验，再经人明确确认 |
| 出厂已验证 SQL 碎片 | 12 条 | 来自一线常用查询；未验证不能出包 |
| 脱敏金标准旧单 | 3 张 | 其中 1 张是主号清单为 0、费用在副卡 |

**可复制价值与转化潜力**

可以沉淀成运营商计费客诉的证据核验能力，供其他一线运维团队复用。复用条件不是换一段提示词，而是换掉该运营商的数据字典、已验证 SQL 碎片、结果字段映射和生产执行规程，并重新验证碎片。核心闭环保持不变：模型规划和核验，人执行 SQL 并确认归档。BE 位于计费系统之上，不替代计费、结算或 CRM。
